# 两个主控入口目录一致性：后端接口核对

日期：2026-11-11（Asia/Shanghai）。状态：只读核对完成，供主控冻结本次小修；未改公共契约或实现。

**本轮 HTTP、归档、业务后端及依赖零变更。** 两个入口应共同展示已有 `nativeProps.deviceData` 的完整真实主控目录，排除原生 `'null'`/空设备取消命令，保持同源元数据与顺序。

## 原因与最小修复

当前 `apps/web/src/extensions/library.ts` 的 `complete` 在主控分区使用：

```ts
item.deviceId !== 'null' && (nativeDevices || controllerIds.includes(item.deviceId))
```

因此顶部设备入口接受完整目录，扩展库主控入口只接受五个 ID。应去掉按入口/`controllerIds` 裁剪目录的条件，共用一个完整主控集合；相同搜索/类型条件下使用相同过滤规则，保持原目录顺序、名称、图标、禁用信息及现有选中/移除行为。当前过滤链另有 `nativeDevices` 的类型过滤旁路，前端修复时须对齐共用数据规则，不能只补齐“全部”列表而留下同条件结果不同。

未知类型条目不能因未登记在五板 `controllerTypes` 中被隐藏；“全部”保留它们，类型选项与归类继续来自可信目录元数据，不猜名称、不伪造能力。原生取消命令继续走独立的安全清空事务，不作为一张主控商品加入任一列表。

## 能力与存储边界

- `controllerIds` 当前是五板自有模块支持矩阵，并被受控串口/设备适配与板型验证复用；**不是整个 OpenBlock 主控可见目录**。本轮保持它及模块 `supportDevice` 原值，不为展示补板而扩大兼容范围。
- 完整目录中的其他主控继续使用已有原生元数据与加载路径；展示不等于新增驱动、编译 profile、实时协议或已验证硬件能力。模块仍按真实兼容矩阵判断，3002 的五板 DeviceId/profile 契约不扩展。
- adapter 已用完整 devices 进行设备存在性/归档恢复校验；无需新增目录 API。继续沿用主控切换、引用阻止、移除事务、模式与手稿保留、busy 及单串口 owner 规则。
- 3001 原样保存完整 `.ob`，不根据前端五板清单裁剪设备字段。项目格式、revision、`cfzn/editor.json`、Hardware HTTP 全部沿用。

## 聚焦验收建议

后续前端/独立测试只需对照两个入口的规范 ID 集合、顺序与元数据；核对同条件搜索/筛选、空命令排除及原生条目保留。选择一个原已存在的非五板条目验证仍走原生路径，并确认六模块不会因此变成兼容；既有选中/移除入口不受影响。无需为本次目录小修扩大硬件或全量 API 测试。
