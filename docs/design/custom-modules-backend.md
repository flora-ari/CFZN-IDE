# 私有自定义硬件模块后端设计

本提案供主控冻结契约。第一阶段由现有 NestJS API 提供本机私有模块库。浏览器凭据只划分匿名模块库，保存完整作品的接口沿用现有契约。未来由服务端身份解析器将已验证的用户身份转换成同一个内部所有者类型。

## 现有边界

| 仓库证据 | 本轮用途 |
| --- | --- |
| [项目控制器](../../apps/api/src/projects/projects.controller.ts) 的 `list`、`read` 和 `readContent` 直接调用单实例 `ProjectStore`。 [Vite 配置](../../apps/web/vite.config.ts) 将不同浏览器发来的 `/api` 请求代理到同一个回环服务。 | 现有项目目录是匿名共享空间。私有模块的元数据、定义和所有者凭据应保存在独立的私有模块库。 |
| [归档校验](../../apps/api/src/projects/project-archive.validator.ts) 校验 ZIP、CRC、边界、项目 JSON 和素材完整性。[本地项目存储](../../apps/api/src/projects/local-project.store.ts) 原样保存提交的归档。 | 项目通过原 `.ob` 保存积木、模式、素材和 `cfzn/editor.json`。自定义模块使用 OpenBlock 的 `project.json.deviceExtensions` 记录已加载的模块版本标识。 |
| [扩展目录](../../apps/web/src/extensions/catalog.ts) 解析归档模块 ID 和兼容板。[外部适配器](../../apps/web/src/extensions/adapter.ts) 包装模块注册与反序列化。[编辑器](../../apps/web/src/openblock.ts) 负责归档备份、恢复和保存状态。 | 加入受信任的本地注册路径。打开项目时先解析所需版本、校验定义和准备真实积木，再进入现有 VM 加载事务。 |

## 本机匿名主体与未来身份接口

1. 私有模块路由由 NestJS 统一解析匿名主体。前端先通过同源 `GET /api/v1/custom-modules` 获取目录并初始化浏览器凭据。服务端生成 32 字节密码学随机令牌，通过 `Set-Cookie` 发送。已有有效凭据时返回原主体的目录。前端等待首次目录请求结束再调用模块 API。同一浏览器首次多标签并行初始化时，共用同源锁并在锁内完成请求，避免覆盖前一个标签刚创建的匿名库。首次发放限定在编辑器同源请求，可依据 `Sec-Fetch-Site` 和请求模式拒绝跨站或导航触发，防止浏览器在未携带原凭据时发起重置。
2. Cookie 使用 `HttpOnly`、`SameSite=Strict`、`Path=/api/v1/custom-modules` 和 host-only 范围，HTTPS 启用 `Secure`。现有回环 HTTP 开发环境只配置受信的编辑器 origin。使用可跨浏览器重启的 Cookie；续期沿用当前主体。Cookie 作用域由主机和路径决定，端口共享 Cookie。单个编辑器 origin 内同一浏览器配置的标签共享匿名库，两个独立浏览器配置或独立 Cookie 容器分别拥有自己的库。清除站点 Cookie 或到期后，初始化得到空的新库。跨浏览器、清除 Cookie 后的恢复和账号迁移属于未来身份接入的范围。
3. 服务端只保存令牌摘要与内部匿名所有者的绑定，或用已签名凭据从受验证的令牌稳定派生内部所有者。采用摘要映射时，先提交绑定，再发送 `Set-Cookie`。使用持久化本地文件以支持服务重启；未知、格式错误或被篡改的凭据应被拒绝。业务层只接收 resolver 返回的 `OwnerScope`，所有者键由服务端生成或派生。Cookie、请求头中的自报身份、请求体和归档内字段有独立解析规则，只有经过服务端验证的凭据可映射到 `OwnerScope`。
4. `POST`、`DELETE` 校验精确的受信 `Origin`，按用途限制请求方法和 JSON 类型。默认使用 Vite 同源代理。私有模块响应和错误使用 `Cache-Control: no-store`；应用日志、错误体和 Location 省略凭据、内部所有者键、定义全文和磁盘路径。Cookie 与 Origin 检查各自验证凭据与浏览器请求来源。
5. 未来让同一身份接口支持已验证用户主体。由网关会话、已验证凭据或受信服务调用解析经认证的发行方、稳定 subject 及适用的 tenant，再映射为服务内部账户作用域。缺少、无效或无法验证的认证凭据返回明确错误。部署使用认证模式时，认证不可用应拒绝访问，防止落入匿名库或暴露其他所有者内容。匿名库的认领由明确授权的迁移处理。当前阶段保留这个注入点，未定义 Python 请求、账号字段或云存储位置。

```ts
interface ModuleIdentityProvider {
  resolve(request: Request): Promise<OwnerScope | null>;
}

// OwnerScope 由服务端身份层构造，供私有模块存储在内部按所有者寻址。
interface PrivateModuleStore {
  list(owner: OwnerScope): Promise<ModuleSummary[]>;
  read(owner: OwnerScope, id: string): Promise<PrivateModule>;
  create(owner: OwnerScope, definition: ValidatedModuleDefinition): Promise<PrivateModule>;
  hide(owner: OwnerScope, id: string): Promise<void>;
}
```

## 私有库 API 与版本

路由和 DTO 命名由主控确定。以下按 `/api/v1/custom-modules` 示意。

| 操作 | 建议行为 |
| --- | --- |
| `GET /` | 初始化匿名浏览器凭据并列出当前主体可见的模块摘要。已隐藏条目从目录中移除。 |
| `POST /` | 接收 `{ definition }`。校验后分配随机 ID 并提交不可变定义。成功后才在目录中出现。 |
| `GET /:id` | 从当前主体取得该 ID 的完整定义，含已隐藏模块。缺少有效身份返回 `401`；ID 不存在或属其他主体时统一 `404`。 |
| `DELETE /:id` | 为当前主体软隐藏该模块。已经隐藏的本所有者条目可幂等返回成功；历史作品仍能按原 ID 读取。属于其他主体或不存在时统一 `404`。 |

同一显示名可由不同主体创建，运行时以随机 ID 寻址。该 ID 同时标识一个不可变版本，使用前端与主控确认的保留前缀及固定字符集，避免与官方扩展和设备身份冲突。积木操作码由受信组件从模块及块标识派生。定义变化可新建模块并取得新 ID，已加载旧版本的作品继续使用原 ID 和原生成语义。升级需要显式移除旧模块或走可验证的积木迁移。

存储沿用本地文件适配理念，使用独立 `private-modules` 根目录和内部 owner scope。每一项操作只打开该 scope 下的记录。可按模块保存一份含不可变定义与软隐藏标记的数据文件，用单进程 `(owner, id)` 锁与临时文件替换保护提交。先持久化完整模块，再发布目录视图。写入失败时，读者只看已提交状态。对定义体积和每个所有者可创建的模块总数设可控上限，超额时返回明确错误。软隐藏保留历史作品所引用的定义，回收要以可验证的历史项目引用为前提。

## 归档与有效执行

- 模块成功加载后，以不可变 ID 注册并加入原生 `deviceExtensions`。存档只引用作品中实际加载的版本，即使尚未拖出块。模块未加载时编辑目录只写私有库。作品保存保留原项目的 revision、dirty 和完整归档语义。
- 打开或导入完整 `.ob` 时，先读取已引用的自定义版本 ID，通过当前身份批量或逐个取得定义并验证兼容板及可用模式。遇到 `404`、服务不可用、定义无效或注册失败时保留当前作品，显示缺少模块或失败原因。加载成功仍沿用现有适配器的 workspace 重建与回滚。使用过的版本即使在目录中隐藏，也可由原所有者在新标签、刷新或服务重启后恢复。旧 `.ob`/`.sb3` 依照原有入口处理。
- `.ob` 是依赖私有库的作品归档。用户可以把文件带到同一个匿名库可访问的浏览器环境。接收者仍须有权取得具体版本。未来如要跨身份移交，定义单独的、由所有者显式发起的包导出或授权流程，再用同一格式校验。当前项目归档省略模块名称、定义、来源 URL 和所有者信息。原匿名项目服务仍能读取作品内的随机模块版本标识、用户写入的积木参数、素材和手写代码草稿。
- 第一阶段私有模块定义采用有版本的严格数据结构，用现有受信适配器构造 Blockly 定义、工具箱与支持的代码生成行为。通过显式字段、枚举、长度、计数、类型及引用校验限制输入。未知字段、冲突 opcode、越界取值和不支持的主控或模式在写入或加载前拒绝。用显示文本 API 渲染模块名称、参数和说明。归档或模块提供的脚本、动态 URL、工具链路径、串口驱动、FQBN 和任意 `eval` 数据应被拒绝。编译仍使用现有受信硬件 profile 和本机执行器，用户显式发起才会提交当前生成或手写代码。模块注册和项目恢复沿用外部 OpenBlock 适配器及 GUI 集成。

## 验收重点

1. 使用两个独立浏览器配置访问同一个实际 NestJS 实例，两边分别创建同名模块。B 持 A 的模块 ID 查询或隐藏时得到 `404`，A 的定义和状态仍可由 A 访问。验证自报 `ownerId`、缺失、无效或伪造的 Cookie、非受信 Origin 的写请求，以及同一配置的标签、重启和 Cookie 清除。
2. 保存包含 A 的模块的作品，随后新建一个定义有变化的同名模块。隐藏旧模块后原所有者仍可打开旧作品并恢复原积木、参数、声音、造型及代码草稿。确认归档只出现正确的模块 ID 与原作品内容，完整保存、下载、磁盘存储保持字节一致。B 打开该归档因缺少模块权限而失败，当前作品和库无副作用。服务重启后 Cookie 与模块快照保持有效。
3. 拒绝错误类型、版本不支持、超额定义、重名 opcode、可执行或可联网字段、路径穿越及注入文本。并发隐藏已使用模块应保持定义可读。模拟写文件或提交失败，目录和已有作品仍指向原快照。
4. 用两个注入的已验证主体测试共享 resolver 与同一存储边界，验证列表、单项和修改的所有者检查。模拟身份解析不可用时拒绝访问。检查公开产物与项目日志中无私有模块定义，确认原有项目 API、内置模块和固定上游 VM 模块字节验证均通过。
