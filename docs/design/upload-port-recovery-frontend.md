# 上传端口选择后的恢复与弹窗可达性

2026-11-23。依据当前源码与主控提供的截图状态进行只读评审。截图中的 Profile 编译、上传均可用且已选 COM3，显示的是“上次上传未开始”的提示。实际是否提交过编译或上传作业，需要结合 HTTP 请求和作业状态确认。

主控补充的本机只读记录显示，当日 15:18 的 ESP32 build `8d82c7ee-c168-46e7-8b92-8c040921d32c` 已 succeeded，尚无对应 upload；15:08 的 FireBeetle upload `21df9ba0-0a76-42e7-92ca-9b59420cab3b` 在 COM3 已 verified succeeded。本提案据此聚焦启动提示恢复和操作按钮可达性，这两条记录由主控核实。

## 当前路径

`nativeUpload → start → HardwareController.start(true)` 在端口为空时同步抛出“请先明确选择本机烧录端口”。此时还没有置 busy、调用 run 或 POST。nativeUpload 将异常存入外层闭包 `uploadError` 并打开上传设置。此后选择端口调用 `hardware.configure`，配置校验成功后发布新快照，但 Progress 的 configure 回调只清局部 `error`。外层 `uploadError` 仅在下一次 start 成功时清空，关闭、重开以及从连接弹窗选择 OS 端口都可能继续显示该历史提示。 [上传入口与错误](../../apps/web/src/native-hardware.ts#L68) · [配置与启动校验](../../apps/web/src/hardware-controller.ts#L167) · [连接弹窗设置端口](../../apps/web/src/connection-modal.ts#L68)

配置完成后用户应再次显式点击“编译并上传”或右侧“上传到设备”，既有 start 会重新检查当前配置及源代码。真实启动后的异步失败存入 `hardware.error`、`job.error` 与日志。所以上次同步启动前失败和真实作业失败已有各自存储位置，修复可以只处理启动前提示。 [作业提交和结果](../../apps/web/src/hardware-controller.ts#L218)

当前 `.cfzn-hardware-modal` 只有 660px/94vw 宽度和 9vh 顶部边距，日志固定高 230px，末尾操作行排在全部配置、错误和日志之后。上游 Modal 把标题和 children 放在内部 Box，打开时锁定背景页面滚动。内容超过视口时，需要本弹窗自己的高度约束和滚动区域。连接弹窗已有独立 max-height/overflow，上传弹窗缺少对应处理。 [现有样式](../../apps/web/src/native-hardware.css#L1) · [上游 Modal 结构](../../.runtime/web-openblock/openblock-vendor/openblock-gui.js#L342866)

## 最小修复建议

1. 将上传前失败提示附上本次尝试的配置身份，即 `deviceId/profileId/portId` 快照。仅当当前配置仍与该快照一致时呈现。成功更改 Profile 或 OS 端口后清除本次启动前提示，同时清局部设置错误，配置失败则保留原配置并显示最新校验原因。用配置身份判定覆盖连接弹窗或主控切换后重新打开的路径。实现可保留在 nativeHardware 视图层。
2. 下一次用户显式点击启动时，成功清除启动前提示，失败替换为本次实际异常。Progress 内的 run 也应结束旧的 nativeUpload 提示，保证一次重试只显示一个当前启动失败原因。主控/Profile/端口变化只更新配置和提示，编译、上传依然由既有 start 入口发起。
3. 当前 Profile 属于所选主控、编译及上传可用，且显式 portId 存在于当前 OS 端口列表时，在既有 busy、模式、源码及串口操作守卫允许范围内，操作区明确显示“已就绪，点击编译并上传”及可用按钮。按钮不能仅凭非空端口字符串判断有效性。保留 start 的最终校验，覆盖刷新后端口消失、Profile 失效以及代码/串口/忙状态检查。就绪提示依据当前状态计算，真实历史作业结果照常可读。
4. 使用上传弹窗专有 class 限定布局，最大高度取 `calc(100dvh - 32px)`，顶部和底部保留视口间距。Modal 内容及内部 Box 采用纵向 flex 和 `min-height:0`，原生标题与关闭按钮占独立固定区域。将硬件设置、状态、错误和日志放入可滚动正文，现有四按钮放在正文外的固定操作栏，白底、可换行。正文和日志保留各自需要的滚动，长 FQBN 和错误换行。操作栏键盘可达且不会被日志内容挤出视口。
5. 实际作业错误、日志、取消中状态、结果未知占有和终端恢复错误继续按现有控制器语义处理。健康检测刷新读取能力和端口，保持显式选择。关闭弹窗继续采用“隐藏（作业继续）”的现有行为，端口配置不触发串口连接或自动上传。

建议产品修改局限于 `native-hardware.ts` 的启动前提示、Progress 配置/重试与正文布局，以及 `native-hardware.css` 的上传专有样式。现有 HTTP、控制器任务执行、VM 和设备传输保持各自契约。

## 聚焦验证规则

- **无端口 → 选择 → 显式重试**。用隔离模拟服务提供可用 ESP32 Profile 与 COM3。清空 OS 端口，点击右侧上传，出现缺端口提示且 POST 为零。实际选择 COM3 后旧提示消失、值保持、按钮可用，选择动作仍为零 POST。用户点击“编译并上传”才产生一次 builds 请求，模拟构建成功后按既有流程产生一次 uploads 请求。
- **另一入口与重新打开**。在连接弹窗选择 COM3，再打开上传设置，按当前配置显示。未改配置而直接关闭、重开时可以保留仍相关的上次启动失败。若刷新后 COM3 已消失，按钮与启动校验按当前列表处理，不能仍宣告可上传。新一次同步失败显示新原因。
- **真实失败保全**。模拟 builds 编译失败、uploads 失败或提交结果未知，确认其作业错误、日志和占有状态保留。重新选择端口只清启动前提示，无法把该作业标为成功。模拟取消继续等待原有终态。
- **真实 DOM 几何**。生产版及隔离 dev 在 1366×768、1024×600、800×600 和至少一档实际浏览器放大下打开上传弹窗。加入多行错误、长 FQBN 和长日志，检查模态上下界在视口内，四个操作按钮可见、可点击，正文可滚动、末尾可达。Tab 可到操作栏，忙时可用隐藏/取消。连接弹窗正常显示。
- **证据界限**。上一轮原生入口模拟测试明确要求健康检测后保留“上次上传未开始”，本轮应更新为“配置仍相关则保留，配置成功改变则清除”的规则，并补无端口到重试的真实 DOM 用例。模拟上传验证 UI、请求次数和恢复流程，实体写入需由主控另行协调。 [已有断言](../../tests/hardware-upload-feedback-20261123.mjs#L160)
