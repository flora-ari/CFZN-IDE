# 两个主控入口的目录一致性前端提案

日期：2026-11-11。仅快速核对与设计，待主控冻结；本轮不修改产品源码，不调查官网，不派工，不启停服务或访问硬件。无新 HTTP 接口。

## 根因

已核对当前 `apps/web/src/extensions/library.ts`、`catalog.ts` 和 `scripts/openblock-hooks.mjs`。顶部原生设备入口与扩展库已经调用同一个 `makeLibraryRenderer`，但 `nativeDevices` 同时承担入口外观和数据分流，造成三处差异：

1. `complete` 的主控分支通过 `nativeDevices || controllerIds.includes(item.deviceId)`，顶部保留全部设备，扩展库仅保留五板。
2. `filtered` 通过 `nativeDevices || …` 跳过顶部入口的类型筛选。
3. 类型行以 `!nativeDevices` 为前提，顶部入口看不到同样的筛选控件。

`controllerIds` 还用于六模块兼容列表、板能力与适配边界，不能为扩大展示列表而扩充它。

## 最小差异

- 两入口主控视图统一使用**已注册的 `nativeProps.deviceData` 完整目录**。应用同一可见规则：排除无设备的取消命令（`null` / `'null'`）及原生明确隐藏的条目；保留真实设备的现有顺序、ID、名称、图标、说明、禁用状态等元数据。不按五板白名单缩减，也不另建第二份目录或重新排序。
- 提取一个主控目录/可见项选择逻辑，供两个入口复用。`nativeDevices` 只决定标题、是否显示大分类导航和返回入口等外观，不再改变主控候选集或过滤语义。
- 使用统一的有效分类键：主控视图始终为 `controllers`。类型选择、清除筛选、原生搜索重置键及卡片映射均使用该键，防止入口标志与残留的舞台/模块分类状态交叉。
- 主控视图在两个入口都显示同样的类型行；移除顶部入口的类型过滤旁路。两边都先从完整可见目录取类型选项，再以“所选类型 AND 原生关键词搜索”缩小结果。同一查询与类型必须得到同一有序结果；继续复用原生搜索，不新建搜索框或跨模态全局搜索状态。
- 当前 `controllerTypes` 仅对已明确登记的五板标记 `board`。没有可靠类型元数据的原生设备不猜成主控板或套件，在“全部”中完整可见；具体类型筛选仅命中已明确分类的条目。没有真实套件条目及元数据就不增加套件选项，也不把未知类型作为隐藏条件。
- 主控卡片继续使用同一选中、移除与适配路径。取消主控仍是明确操作，不作为硬件商品混入列表；保留模块依赖/积木引用拒绝、忙碌与硬件作业守卫、模式保留及失败回滚。其他原生板的展示不等于新增模块兼容、实时协议或编译烧录能力。

预计产品改动仅涉及 `library.ts` 中目录选择、有效分类和筛选控件条件；如抽取纯选择器，可放现有前端扩展目录。无需改 GUI hooks、VM、后端、归档或硬件能力表。以主控冻结后的实际实现为准。

## 聚焦验收

1. 两入口进入主控视图、类型为全部且查询为空时，与同一份已注册目录的可见硬件投影逐项比较：有序 ID 完全一致，关键元数据一致，取消命令不出现，顶部原有真实板不丢失。不能仅比较数量。
2. 两入口都可操作类型与原生搜索；相同条件得到同一有序 ID 列表。未知类型板可在全部及名称搜索中找到，主控板筛选只命中明确分类项；清除筛选恢复完整目录。
3. 从任一入口选板后，另一入口显示同一当前主控；重复选择保持幂等。已选项的移除入口、依赖/引用拒绝、编程/上传模式和工具箱类别继续沿用现有行为。
4. 选择五板之外的原生设备时，模块兼容判断仍按原有 `supportDevice`；不因目录统一变为支持。保留禁用条目状态，不启动连接、串口或硬件作业。
5. 开发后完成适当的前端类型检查/构建，并用隔离浏览器在 Vite dev 与 static dist 核对上述短链；确认改动没有进入 VM 模块。无需扩大到官网、商城或全量硬件回归。

本提案确认主控拟定方向可用；冻结点仅为完整目录的统一投影及共同筛选语义，其余 v0.5/v0.6 成果保持。
